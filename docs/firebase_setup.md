# Firebase Setup

Everything in this file is run **once, by the owner of the app**, against their
own Google account. None of it can be automated from the repository: creating a
project, enabling a sign-in provider and generating `lib/firebase_options.dart`
all authenticate as a human, and `flutterfire configure` writes keys only the
project owner can mint.

Until step 5 has been run, `lib/firebase_options.dart` does not exist and
`flutter analyze` reports unresolved imports. That is expected, not a bug to
work around with a stub.

The backend surface, in full: Firebase Auth with Google as the only provider,
and three Firestore documents per user.

```
users/{userId}                      name, email, photoUrl, createdAt
users/{userId}/settings/board       homeZoneId, locations[], revision, updatedAt
users/{userId}/settings/preferences theme, palettes, hourFormat, workingHours,
                                    locale, revision, updatedAt
```

See [specs/auth.md](specs/auth.md) and [specs/sync.md](specs/sync.md).

---

## Files in this repository

| File | What it is |
|---|---|
| `firestore.rules` | The security rules: owner-only subtree, deny everything else. |
| `firestore.indexes.json` | Intentionally empty. See "Why no indexes". |
| `firebase.json` | Points the CLI at the two files above. No hosting block. |
| `.firebaserc.example` | Template for `.firebaserc`, which names *your* project. |
| `lib/firebase_options.dart` | Generated by step 5; generate your own. |

## Prerequisites

```bash
npm install -g firebase-tools
firebase login
dart pub global activate flutterfire_cli
```

---

## 1. Create the project

<https://console.firebase.google.com> then **Add project**. Any display name;
note the **project id** it generates, because every step below wants it.

Google Analytics is not needed: nothing in the app reads it, and it adds a
second consent surface to a tool that collects nothing.

## 2. Enable Google sign-in

**Authentication -> Get started -> Sign-in method -> Google -> Enable.** Set a
project support email and save.

Do not enable Email/Password or any other provider. The app is Google-only by
design ([specs/auth.md](specs/auth.md)), and a provider enabled in the console
but unreachable in the UI is an account-recovery surface nobody tested.

## 3. Authorise the GitHub Pages domain

**Authentication -> Settings -> Authorised domains -> Add domain:**

```
guilhermeeng99.github.io
```

Host only. No `https://`, no `/timebuddy/` path: the list matches origins, and
an entry carrying a path is silently never matched.

`localhost` is authorised by default, so sign-in works on your machine before
you ever open this list. **That is what makes this step dangerous**: the first
failure happens after a green local test, and the error is
`auth/unauthorized-domain`, which the redirect flow surfaces as a bounce back
to onboarding with no signed-in user and, depending on the browser, no visible
message at all. If sign-in works locally and does nothing in production, check
this first.

## 4. Create the Firestore database

**Firestore Database -> Create database -> Production mode.** Production mode
starts locked, which is correct: step 6 uploads the real rules a minute later,
and starting in test mode opens a window where the database is world-readable.

Pick the region closest to your users (`southamerica-east1` for Brazil). **The
region is permanent** — changing it later means a new project.

## 5. Wire the Flutter app

```bash
flutterfire configure --project=<project-id> --platforms=android,web
```

This registers the Android app (package `com.guiga.timebuddy`) and the web app,
then writes `lib/firebase_options.dart` and `android/app/google-services.json`.
Both are safe to commit: the web API key is public by design, it identifies the
project and authorises nothing. What protects the data is `firestore.rules`,
which is why step 6 is not optional.

### Android only: register your signing fingerprint

Google sign-in on Android checks the app's signature. Without a matching SHA-1
in the console the plugin fails with `ApiException: 10 (DEVELOPER_ERROR)`, which
says nothing about fingerprints.

```bash
cd android && ./gradlew signingReport   # take the SHA-1 of the debug variant
```

**Project settings -> Your apps -> Android -> Add fingerprint.** Repeat with the
release keystore before publishing.

## 6. Deploy the rules

```bash
cp .firebaserc.example .firebaserc      # then put your project id in it
firebase deploy --only firestore:rules,firestore:indexes
```

`.firebaserc` is deliberately not in the repository: it names one person's
project, and a committed one silently redirects a contributor's deploy into
someone else's database. Add `.firebaserc` to `.gitignore` the first time you
create it, since nothing ignores it today. `firebase use --add` writes the same
file if you prefer the interactive route.

Re-run this deploy after **any** edit to `firestore.rules`. The rules being
enforced are the ones in the console, never the ones in the working tree.

## 7. Verify

1. `flutter run -d chrome`, sign in with Google, the app opens on the grid.
2. Console -> Firestore: `users/{yourUid}` exists, with `settings/board` and
   `settings/preferences` under it.
3. Push to `main`, wait for the Pages deploy, then sign in at
   <https://guilhermeeng99.github.io/timebuddy/>. This is the check step 3
   exists for; do not skip it because localhost worked.

## Why no `hosting` block in `firebase.json`

The web build is deployed to **GitHub Pages** by
`.github/workflows/deploy-pages.yml`, and that is a recorded decision
([roadmap.md](roadmap.md), 2026-08-19). Firebase here is Auth and Firestore
only, and both are reachable from any origin once step 3 is done.

Do not add a `hosting` block "for completeness". Two hosts for one bundle means
two URLs that can disagree about which build is live, and the Firebase one would
be served without the `--base-href /timebuddy/` the Pages build is made with, so
it would ask for its assets where nothing answers.

Revisit only if the app ever needs a server-side redirect or a rewrite rule,
which a hash-routed SPA does not.

## Why no indexes

`firestore.indexes.json` is an empty index set, and it should stay empty.

Every read this app performs is a document read by id: two documents on sync,
one profile on sign-in. Firestore needs no index for that, so there is nothing
to declare. The file exists so `firebase deploy` has something to point at, and
so an index someone adds by hand in the console is removed by the next deploy
instead of living on invisibly.

An index file that quietly grows is how a project ends up paying for queries
nobody makes. If a new index ever looks necessary, answer first which query
needs it and why the app is querying at all rather than reading a document whose
id it already knows.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Sign-in works on localhost, silently fails on the live site | Step 3, `auth/unauthorized-domain`. |
| Android: `ApiException: 10` | Missing SHA-1 fingerprint, step 5. |
| `PERMISSION_DENIED` on every read after sign-in | Rules never deployed (step 6), or the database is still on the locked production defaults. |
| `flutter analyze`: `firebase_options.dart` not found | Step 5 has not been run in this checkout. |
| `firebase deploy` hits the wrong project | `.firebaserc` missing, or still holding the placeholder id (step 6). |
| Web sign-in loops back to onboarding in Safari or Firefox | Not the rules. The redirect flow round-trips through `<project>.firebaseapp.com`, and browsers that partition third-party storage can drop the state on the way back. The documented fixes are a popup fallback or serving the auth handler from the app's own origin, which GitHub Pages cannot do. |
