# Locations & Board Spec

The board is the user's list of places. Every other feature reads it: the grid
draws one row per location, the world clock one tile per location, and the
converter uses it as its target set. (The meeting planner was a fourth reader;
it has been deleted.)

This spec owns the saved-location entity, the city catalog behind the search, and
the `BoardCubit` that is the single source of truth for "which places is this
user watching".

**The board has no screen of its own.** It used to: a Cities destination whose
whole content was the list, its order and its row actions. It was removed, and
the reason is worth keeping — it showed the same list the grid already shows,
one tab away, so a user who wanted to move a city looked at their cities twice.
Editing now happens where the board is being read:

| Capability | Where it lives |
| --- | --- |
| Reorder | Drag a row label on the grid, or a tile on the world clock |
| Set as home / replace zone / remove | Tap a row label on the grid; the world clock's detail sheet |
| Add | The FAB on either, and the `/add` route behind it |
| How full the board is | The add sheet's header, where the cap is about to matter |

The interactions themselves are one library, `board_actions.dart`, rather than
a copy per screen — two copies of a five-second undo window is how it becomes
four seconds on one of them.

## Entity Contract

```dart
SavedLocationEntity {
  id:          String   (required, uuid v4, generated on add)
  zoneId:      String   (required, IANA identifier: the only field the engine reads)
  label:       String   (required, display name, e.g. "Sao Paulo")
  countryCode: String   (required, ISO 3166-1 alpha-2, e.g. "BR")
  sortIndex:   int      (required, 0-based position on the board)
  addedAt:     DateTime (required, UTC)
}

BoardEntity {
  homeZoneId: String                     (required, the reference zone, see rule 3)
  locations:  List<SavedLocationEntity>  (required, ordered by sortIndex)
  revision:   int                        (required, incremented on every write, see sync.md)
  updatedAt:  DateTime                   (required, UTC)
}
```

`label` and `countryCode` are **denormalized** from the catalog at add time. The
catalog can change between app versions (cities renamed, entries dropped); a
board must keep rendering regardless. Only `zoneId` is authoritative, and it is
resolved through `zoneOrNull` before it is ever stored and canonicalised again
on every load, so two spellings of one clock cannot become two rows.

Equatable by all fields. `copyWith` on both.

### City catalog

```dart
CityEntity {
  zoneId:      String  (required, canonical IANA identifier)
  name:        String  (required, English name, stored without diacritics)
  countryCode: String  (required, ISO 3166-1 alpha-2; `ZZ` marks the one
                        non-country row, `UTC`)
  countryName: String  (required, also matched by search)
  admin1:      String? (nullable, state/province, disambiguates "Springfield")
  prominence:  int     (required, search weight: higher sorts first)
  aliases:     List<String> (required, may be empty, e.g. ["NYC"] for New York)
}
```

`isCurated` is `prominence > 0`. Prominence is assigned in bands by the seed
table (100 for a global hub, 85 to 99 for a major world city, 70 to 84 for a
capital or large regional centre, and down from there), never measured, because
the question it answers is "which of these did the user probably mean", which is
a judgement about familiarity rather than a population figure. **Zero means the
row was derived from the zone id rather than curated**, and that is also what
tells the default list which rows are worth suggesting.

There is no population column and no local-script name. A population figure
would be a second dataset to keep current, and it would rank Chongqing above
Zurich for an audience far more likely to be typing the second. Local spellings
are carried as `aliases` instead, so "Lisboa" finds Lisbon without giving the
list a second name to render.

The catalog is a static asset at `lib/app/assets/data/cities.json`, generated by
`scripts/build_city_catalog.dart`. It is parsed once, on the first read, into an
in-memory index (62 KB on disk) and never written at runtime.

**The catalog is derived from the shipped tz database, not joined against a
public city dataset.** The usual recipe joins GeoNames or similar against the
zone list on coordinates or on a country column, and a mis-joined row does not
fail: it ships a city pointing at a plausible neighbouring zone and shows an
hour that is wrong for half the year. Here the IANA id *is* the authority on
which clock a place keeps, so deriving the catalog from the database cannot
produce that class of error at all, and the build stays offline, dependency-free
and reproducible (its output is sorted and its JSON keys are in a fixed order,
so regenerating without changing an input produces a byte-identical file).

What that costs is that the database knows the id and nothing else: it does not
know what country `Asia/Kuching` is in and it has never heard of Mumbai. So a
derived row's country comes from a hand-written allow-list in the script, its
display name is the last id segment with the underscores taken out, and a zone
absent from that allow-list is not emitted at all. The curated table in
`scripts/city_seeds.dart` is the answer to all three: a seed overrides its
derived row in every field, and adds the cities that have no zone of their own
because they share a clock with a neighbour (Rio de Janeiro, Mumbai, Frankfurt).

The shipped file holds **500 rows: 254 curated and 246 derived.** A further
**92 database names are deliberately not emitted**, and the build prints every
one of them so a tzdata upgrade cannot add or drop a city behind our backs. They
are the legacy aliases of entries that are already in the catalog under their
current name (`America/Buenos_Aires` beside `America/Argentina/Buenos_Aires`,
`Africa/Asmera` beside `Africa/Asmara`, `Asia/Calcutta` beside `Asia/Kolkata`)
and the legacy groupings that are not places at all (`US/Pacific`,
`Brazil/East`, `Australia/NSW`). Both would otherwise become rows that look like
separate cities and are not. `Etc/*` and the bare offset spellings (`CET`,
`EST5EDT`) are dropped for the same reason: nobody searches a clock app for
`Etc/GMT-14`. Plain `UTC` is the one exception and comes back in as a seed,
because picking a neutral reference is a real thing to want.

Several cities legitimately share one `zoneId`: Oslo, Stockholm and Copenhagen
all read `Europe/Berlin`. That is intended, and rule 2 is what keeps two of them
off the board at once.

## Business Rules

1. **There is one board per install, and nothing in this feature takes a user
   id.** No shared board and no public board. The document is written locally
   and *mirrored* to the account, never addressed by account: the id that
   mirroring needs is session state and lives in `SyncCoordinator`, so no
   entity, repository method or cubit in this feature carries one. See the
   Repository Contract.

   This rule used to say "local-only until M3 attaches the sync layer… there is
   no `AuthBloc` to resolve one from yet". The sync layer attached; the shape
   did not change, which is why the rule now reads as a decision rather than as
   a wait.

2. **A location is identified by its zone, not by its city.** Adding "Sao Paulo"
   and then "Rio de Janeiro" (both `America/Sao_Paulo`) is **rejected** with a
   `DuplicateZoneFailure` that names the existing row. Two rows showing identical
   times is noise, and the grid has no way to distinguish them.

   The comparison is between **canonical** zone ids, resolved through
   `zoneOrNull`, never between the spellings as written
   (`BoardEntity.locationForZone`). Oslo and Berlin are one clock under two
   names, and `Asia/Calcutta` is `Asia/Kolkata`, so comparing raw spellings
   would let both onto the board as two rows showing identical times, which is
   precisely what this rule exists to prevent. An id the tzdata cannot resolve
   at all falls back to a literal comparison, so two genuinely unknown zones
   stay distinct instead of collapsing into each other.

3. **Home is a zone id, not a board row.** `homeZoneId` is the reference every
   relative offset is measured against. It may or may not also appear in
   `locations`. On first launch it is seeded from `TimeZoneEngine.deviceZone()`
   and written to storage immediately, because an unwritten seed would be
   re-derived from whatever zone the device reports next time, silently moving
   the reference the whole board is measured against as soon as the user
   travels.

4. **The board caps at 20 locations.** Beyond that the grid stops being readable
   and the per-tick rebuild cost stops being trivial. Adding a 21st returns
   `BoardFullFailure`. The cap is `BoardEntity.maxLocations`, not a scattered
   literal, so the domain guard, the failure and the "3 of 20" header can only
   ever disagree by someone editing one line.

5. **Order is user-controlled and explicit.** `sortIndex` is dense and 0-based.
   Reordering rewrites the indices of the affected range in one write, never one
   write per row.

6. **An empty board is a valid state**, not an error. Every consumer renders
   `FeatureEmptyState` with an "add your first city" CTA. The grid does not crash
   on zero rows, and the world clock shows only the home clock.

7. **Removing a location is immediate and undoable via snackbar** for 5 seconds.
   No confirmation dialog: the action is cheap to reverse and a dialog per
   removal is friction on the app's most common edit.

8. **Removing the home zone's row does not clear `homeZoneId`.** They are
   independent (rule 3). The relative offsets keep working.

9. **Search matches on name, aliases, country and state**, accent- and
   case-insensitively, through `normalizeForSearch()`
   (`lib/core/utils/string_normalize.dart`). Ranking is: exact name, exact
   alias/country/state, name prefix, other prefix, name substring, other
   substring; ties break by descending `prominence`, then by name so the order
   is stable across runs where many derived rows sit at 0. A name match outranks
   an alias, country or state match of the same shape, so typing `paris` puts
   the city above every row in a country whose name merely contains it. "sao
   paulo", "SAO PAULO" and "são paulo" must all find the same city.

   Both sides of every comparison are folded, and the index is folded once at
   parse time rather than per keystroke: search runs on every character typed,
   and folding 500 names inside that loop would put `normalizeForSearch` on the
   critical path of typing.

10. **Search also accepts a raw IANA id.** Typing `Asia/Tokyo` finds Tokyo, in
    any casing, and `_` reads as a space so `America/Sao Paulo` works too. Power
    users and pasted values should not dead-end. A full id ranks as an exact
    match and returns every city on that clock; a *partial* id ranks last, and
    only when the query contains a `/`, because without that gate every city
    sharing a zone would answer to whichever city the id is spelled after and
    `sao paulo` would return Rio de Janeiro.

11. **A location whose zone no longer resolves is kept and flagged**, never
    silently dropped. `BoardLoaded.unresolvedIds` carries the offending **zone
    ids** (the fact is about the zone, and two rows in one dropped zone are one
    entry), and the UI renders those rows greyed with a "zone unavailable" note
    and a replace action. Dropping rows on a tzdata upgrade would delete user
    data without consent.

12. **The catalog is never the source of truth for a saved row.** After a catalog
    regeneration, existing boards keep their stored `label`. The one sanctioned
    way a stored label changes is an explicit `replaceZone`, which is also the
    repair offered for rule 11.

## Repository Contract

```dart
abstract class BoardRepository {
  /// Reads the stored board, seeding and persisting an empty one when nothing
  /// has been written yet. [homeZoneIdFallback] is consulted only for that
  /// first seeding and for a document with no `homeZoneId` at all.
  Future<Either<Failure, BoardEntity>> load({
    required String homeZoneIdFallback,
  });

  /// Persists [board] as given. There is no per-row endpoint: the document is
  /// one unit under 10 KB and partial writes would need a merge strategy for
  /// no gain.
  Future<Either<Failure, BoardEntity>> save(BoardEntity board);
}

abstract class CityCatalogRepository {
  /// Loads and parses the asset. Idempotent, cached in memory.
  Future<Either<Failure, List<CityEntity>>> load();

  /// Ranked search. Returns at most [limit] results. See rules 9 and 10.
  /// An empty or whitespace-only query returns the curated rows, most
  /// prominent first: a derived row carries a mechanical name and a
  /// best-effort country, which is fine as a hit and poor as a suggestion.
  Future<Either<Failure, List<CityEntity>>> search(String query, {int limit = 30});
}
```

**No `userId`, and the signatures did not grow when the remote half landed.**
This spec used to predict that sync would add a `userId` to both methods and a
`forceRefresh` to `load`. Sync shipped and neither happened, because the account
is *session* state: `SyncCoordinator` (`lib/core/sync/sync_coordinator.dart`)
holds it, `BoardRepositoryImpl` takes the coordinator and hands it the saved
document, and no caller of this contract has to know who is signed in. A
`userId` here would have travelled into every one of them — the cubit, the
settings page, the sync service's own re-save — and made each resolve a session
from `AuthBloc`. It is also what keeps a guest and a signed-in user on one code
path ([guest_mode.md](guest_mode.md) rule 1).

`forceRefresh` never arrived either, for a sharper reason: there is no
reconciling read on this contract at all. `SyncService` owns the conflict
ladder for both documents and writes the winner back into local storage, so a
screen calling `load` after a sync already reads the reconciled copy. A `load`
that pulled the remote copy itself would be a second owner of that ladder.
[preferences.md](preferences.md) records the same decision for its own
repository.

**Bumping `revision` and stamping `updatedAt` is the caller's job**, not the
repository's. `BoardCubit` does it in one place for every mutation. A repository
that restamped would inflate the very revision a sync is trying to reconcile.

**Cache strategy:**

- `load` reads `shared_preferences` only, so the app opens with no network wait.
  Nothing written yet means an empty board seeded from `homeZoneIdFallback` and
  persisted at once (rule 3).
- `save` writes `shared_preferences` first and that write decides the answer. A
  refused write is a `StorageFailure` the caller must handle, because the state
  has already moved (see State Machine).
- The remote write runs **behind** that answer: `save` hands the board to
  `SyncCoordinator.pushBoard` without awaiting it, because a reorder that waited
  on a Firestore round trip would freeze the list for as long as the network
  felt like taking. A failed remote write is never a `Left` — the coordinator
  swallows it and sets the dirty flag, and `SyncService` retries on the next
  start, sync or resume. See [sync.md](sync.md) rules 2, 3 and 4.
- A build with no signed-in account behaves exactly like a signed-out one: the
  local write lands and nothing is marked dirty.

## Model Serialization

`BoardModel` extends `BoardEntity`. The same JSON shape is used for
`shared_preferences` today and for Firestore from M3, so there is one
serializer, not two — `shared_preferences` locally and Firestore remotely. The
stored document lives under the versioned key
`timebuddy.board.v1`.

| JSON field | Dart field | Notes |
|---|---|---|
| `homeZoneId` | `homeZoneId` | `String`; **missing** degrades to the passed fallback, but a present id the tzdata cannot resolve is kept verbatim |
| `locations` | `locations` | `List<Map>`; a malformed entry is skipped, not fatal |
| `revision` | `revision` | `int`; missing degrades to `0` |
| `updatedAt` | `updatedAt` | epoch-millisecond `int` (an unwrapped Firestore `Timestamp`) or ISO-8601 string, both to UTC `DateTime`; unreadable falls back to the epoch |

An unresolvable home zone is kept rather than swapped for the device zone
because the grid detects exactly that case and shows a banner asking the user to
fix their home city (time_grid.md). Substituting here would make that banner
unreachable and would silently move the reference zone of every offset on
screen. An unreadable timestamp falls back to the epoch and never to "now", so a
value nobody can read loses every tie it enters instead of winning them by
looking freshly written.

`SavedLocationModel` fields map 1:1. `addedAt` follows the same dual encoding.

**Defensive parsing is mandatory** on both boundaries. A non-map entry, or a
missing `id`, `zoneId` or `sortIndex`, drops that one row and keeps the rest:
those three are load-bearing, since `id` addresses the row for every mutation,
`zoneId` is the only field the engine reads, and `sortIndex` places it. `label`
and `countryCode` are display data, so a missing one degrades (to the zone id,
and to the empty string) rather than deleting a real location. The board is the
user's whole state; one bad field must not cost them the list.

**The surviving rows are re-sorted and re-densified on read**, so the list a
consumer sees always satisfies rule 5. Without that, rows left at 0, 2, 3 by a
dropped entry would make the next add take index 3 and collide. The repaired
order rides along with the next save, so the document heals itself.

## State Machine

### BoardCubit

Session-scoped: `AppShell` creates it once per session and eagerly calls
`load()`. Every page reads that one instance, which is what keeps the board list
and the grid showing the same order.

```dart
sealed class BoardState extends Equatable
BoardInitial
BoardLoading
BoardLoaded({ board: BoardEntity, unresolvedIds: Set<String>, isSyncing: bool })
BoardError({ failure: Failure })
```

`unresolvedIds` holds **zone ids**, not row ids (rule 11).

**Nothing sets `isSyncing`.** It defaults to `false` and no code path in `lib/`
ever passes anything else. It was carried in anticipation of the passive sync
indicator, and the indicator arrived somewhere else: `SyncStatusRow` subscribes
to `SyncService.status` directly, because the status belongs to the sync layer
and a board state that mirrored it would be a second copy of one fact — one
that goes stale for every screen not looking at the board. The field stays
because the shape it reserves is still the right one if a board-local
"uploading" affordance is ever wanted, and because removing it from `props` is
a change to state equality; nothing in the app reads it today.

**Transitions:**

```
BoardInitial ──load()───────────────────→ BoardLoading → BoardLoaded(board)   [stored or freshly seeded]
                                                       → BoardError(failure)   [the document could not be read]

BoardLoaded ──addCity(city)─────────────→ BoardLoaded(board + row)    [optimistic, then persist]
BoardLoaded ──removeLocation(id)────────→ BoardLoaded(board - row)    [optimistic, undo for 5s]
BoardLoaded ──undoRemove()──────────────→ BoardLoaded(board + row)    [re-checks the cap and rule 2]
BoardLoaded ──reorder(old, new)─────────→ BoardLoaded(board reindexed)
BoardLoaded ──setHome(zoneId)───────────→ BoardLoaded(board)
BoardLoaded ──replaceZone(id, city)─────→ BoardLoaded(board, row repointed)

any mutation refused ────────────────────→ BoardLoaded(previous board) + returns the Failure
```

**A rejected mutation is returned, not emitted.** Every mutation is
`Future<Failure?>`: `null` when it landed, the failure when it did not, and the
page that called it is what shows the snackbar. Two reasons, both load-bearing.
A failure parked on `BoardLoaded` has to be cleared by somebody, and missing
that clears nothing while re-firing on the next unrelated rebuild; and every
listener would see it, so two mounted pages would raise two snackbars for one
refused add. Returning it hands the failure exactly once to the caller that
caused it. `BoardError` stays reserved for a `load()` that produced no board at
all: emitting it for a duplicate city would blank a screen the user is reading
over a message that belongs in a snackbar.

The refusals a caller must expect are `DuplicateZoneFailure` (rule 2, carrying
the label of the row that already covers the zone), `BoardFullFailure` (rule 4,
carrying the cap), a `ValidationFailure` for a zone id the tzdata does not know,
and a `StorageFailure` from the write itself. `boardWriteFailureMessage` in
`add_location_sheet.dart` is the single mapping to copy, so the picker and the
board list cannot explain the same refusal differently.

**Mutations are optimistic.** The state updates first, persistence follows, and
a refused write rolls the state back to exactly what it was. Users reorder
cities by dragging, and a row that snaps back because a write is in flight feels
broken. `reorder` drops a no-op or an out-of-range move silently, because a
widget's drag convention is not something to snack at the user about.

**One commit path applies the invariants.** Every mutation funnels through it,
so no mutation can forget to redensify `sortIndex` (rule 5), bump `revision` or
stamp `updatedAt`.

The five-second undo window belongs to the snackbar, not to the cubit: the cubit
holds only `lastRemoved`, because a timer here would fire against a widget tree
that may already be gone. `undoRemove` re-runs the cap and duplicate checks,
since the window is the user's and the board may have changed underneath.

### LocationSearchCubit

Page-scoped, created by the add-location sheet.

```dart
LocationSearchInitial
LocationSearchLoading
LocationSearchResults({ query: String, cities: List<CityEntity> })
LocationSearchEmpty({ query: String })
LocationSearchError({ failure: Failure })
```

`LocationSearchError` is what the "catalog missing or corrupt" edge case needs:
folding a broken catalog into `LocationSearchEmpty` would tell the user their
query matched nothing when nothing was searched, and the suggested fix ("try a
time zone id") would never work.

Debounce is 200 ms, long enough that a touch-typist's "sao paulo" is one search
instead of nine and short enough that a deliberate typist never notices it. It
lives in the cubit rather than in the search field, so it is testable. Each read
carries the generation it started in and drops its result if a newer keystroke
has begun since: the catalog is a list in memory, and nothing orders two reads
of it.

An empty or whitespace-only query returns a curated default list rather than
nothing, so the sheet is useful before typing. That list is the most prominent
city of each **IANA region**, most prominent first, derived from the first
segment of the zone id (`America/`, `Europe/`, `Pacific/`) because no catalog
field carries a continent and a hand-maintained continent table would be a
second place to be wrong about where a city is. The cubit builds it from
`load()` rather than from `search('')`, whose own empty-query answer is the
curated rows ranked by prominence alone and so would offer several cities from
the same region. It is computed once per sheet and cached, so clearing the field
costs no second catalog read.

## Performance

The catalog asset is read and decoded **once**, and two keystrokes racing a cold
catalog share the one in-flight read rather than decoding the file twice. A read
that failed is not cached, so the sheet's retry is a real one.

Both methods then walk the same in-memory index, whose search keys are folded at
parse time (rule 9). A linear walk over 500 rows per keystroke is cheap; a trie
or an inverted index would be a second structure to keep correct for a list this
size, and the expensive part was never the walk, it was folding the strings.

The sheet's default list is grouped once per sheet and cached, and results are
capped at `limit` before they reach a widget, so the picker builds at most 30
rows and does so lazily.

## Edge Cases

- **First launch, device zone detected** → board is created with `homeZoneId` =
  device zone and an empty `locations` list, and written to storage at once
  (rule 3). The empty state invites the first add.
- **First launch, device zone detection failed** → `deviceZone()` answers `UTC`
  with `isFallback: true`, and that is what seeds the board. There is still no
  dedicated prompt: `UTC` resolves, so it is a working reference rather than a
  broken one, and the grid's home-zone banner is reserved for an id that does
  not resolve at all. The `pickHomeTitle` / `pickHomeMessage` copy is in place
  for the prompt when it lands.
- **Adding the home city as a row** → allowed. Users want their own time in the
  grid alongside the others.
- **Adding a second city in the same zone** → rejected, rule 2, with a snackbar
  naming the row that already covers it. The sheet stays open, so the user can
  pick something else without reopening it.
- **Board at the 20-city cap** → the add button stays enabled but the sheet shows
  the cap message on selection, so the user learns why rather than facing a dead
  control. The board header states the count against the cap, so a user who
  meets `BoardFullFailure` should have seen it coming.
- **A removal is refused by the write** → the board rolls back and the undo offer
  is not shown at all. Offering to undo a removal that never happened would put
  the board one accepted tap away from being wrong.
- **The board changed during the undo window** → `undoRemove` re-checks the cap
  and rule 2 and refuses rather than forcing the row back.
- **A saved zone id was renamed upstream** → `zoneOrNull` resolves the alias
  (timezone_engine rule 4) and `BoardCubit` canonicalises it on load; the
  repaired id rides along with the next save. Transparent to the user.
- **A saved zone id no longer exists at all** → rule 11: kept, flagged, greyed,
  replaceable.
- **Catalog asset missing or corrupt** → both `CityCatalogRepository` methods
  return `Left(ServerFailure)`; the board still renders from stored labels, and
  only the add-location sheet shows the error, with a retry. A broken catalog
  must not take down the app. A failed read is not cached, so the retry is a
  real one.
- **A single catalog row is malformed** → that row is skipped and the rest stays
  searchable. Finding 499 of 500 cities beats finding none.
- **Search query is a raw zone id with wrong casing** (`asia/tokyo`) → normalized
  and matched, rule 10.
- **Two devices reorder concurrently** → last write wins by `revision`
  ([sync.md](sync.md) rule 6). The losing device's order is overwritten on its
  next sync. This is behaviour now, not a plan.

## Storage

**The read path**, and the one every screen depends on: one
`shared_preferences` string under `timebuddy.board.v1`, holding `homeZoneId`,
`locations[]`, `revision` and `updatedAt`. A document that is not even a JSON
object is reported as a `StorageFailure` rather than silently replaced, so the
repository decides whether to seed or to surface it; a malformed *row* inside a
readable document never throws.

**The remote mirror**, in the same JSON shape so one serializer feeds both:

**Document:** `users/{userId}/settings/board`

Fields: `homeZoneId`, `locations[]`, `revision`, `updatedAt`.

Read and written by document id only. No composite indexes. See
[sync.md](sync.md).

All copy under `t.locations.*`. Rendered today:

- `t.locations.addTitle`
- `t.locations.countLabel(count, max)`
- `t.locations.searchHint` / `searchNoResults`
- `t.locations.duplicateZone(city)` / `boardFull(max)`
- `t.locations.removed(city)` / `undo`
- `t.locations.unresolvedZone` / `replaceZone`
- `t.locations.setAsHome` / `homeLabel`

**Dead copy**, kept in the JSON but with no call site anywhere in `lib/`:

- `t.locations.title`, `emptyTitle`, `emptyMessage`, `emptyCta` and
  `reorderHint` are **deleted**, along with `t.nav.locations`. All six belonged
  to the **Cities page**, which was removed (see the top of this spec): the
  grid and the world clock draw their own empty states from their own
  namespaces, and reordering is a long-press on a grid row with no hint line
  above it. Copy kept against a screen that is not coming back is copy every
  future translator prices twice.
- `t.locations.pickHomeTitle` / `pickHomeMessage` — reserved, not orphaned:
  they are the copy for the "device zone was not detected" prompt described
  under Edge Cases, written ahead of the screen that will show them.

Neither group is deleted here. A translated string costs nothing to keep and
the Cities set is the exact copy a future manage-board screen would ask for;
what matters is that nobody reads this list and assumes a page exists behind
it.

The row actions sheet reuses `t.common.remove`, and a write that simply did not
land falls back to `t.common.errorBody`: the board has already rolled back, so
the generic message is the honest one.
