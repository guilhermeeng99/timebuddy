# Locations & Board Spec

The board is the user's list of places. Every other feature reads it: the grid
draws one row per location, the world clock one tile per location, the planner
and converter use it as their target set.

This spec owns the saved-location entity, the city catalog behind the search, and
the `BoardCubit` that is the single source of truth for "which places is this
user watching".

---

## Entity Contract

```dart
SavedLocationEntity {
  id:          String   (required, uuid v4, generated on add)
  zoneId:      String   (required, IANA identifier: the only field the engine reads)
  label:       String   (required, display name, e.g. "Sao Paulo")
  countryCode: String   (required, ISO 3166-1 alpha-2, e.g. "BR")
  sortIndex:   int      (required, 0-based position on the board)
  addedAt:     DateTime (required, UTC)
}

BoardEntity {
  homeZoneId: String                     (required, the reference zone, see rule 3)
  locations:  List<SavedLocationEntity>  (required, ordered by sortIndex)
  revision:   int                        (required, incremented on every write, see sync.md)
  updatedAt:  DateTime                   (required, UTC)
}
```

`label` and `countryCode` are **denormalized** from the catalog at add time. The
catalog can change between app versions (cities renamed, entries dropped); a
board must keep rendering regardless. Only `zoneId` is authoritative, and it is
validated through `zoneOrNull` on every load.

Equatable by all fields. `copyWith` on both.

### City catalog

```dart
CityEntity {
  zoneId:      String  (required, IANA identifier)
  name:        String  (required, English name)
  nameLocal:   String? (nullable, local-script name, used as a search alias only)
  countryCode: String  (required)
  countryName: String  (required)
  admin1:      String? (nullable, state/province, disambiguates "Springfield")
  population:  int     (required, drives search ranking)
  aliases:     List<String> (required, may be empty, e.g. ["NYC"] for New York)
}
```

The catalog is a static asset at `lib/app/assets/data/cities.json`, generated by
`scripts/build_city_catalog.dart` from a public city dataset joined against the
tzdata zone list. It ships roughly 400 entries: every zone's largest city plus
well-known secondary cities. It is parsed once at startup into an in-memory list
(under 200 KB decoded) and never written at runtime.

## Business Rules

1. **A board belongs to exactly one user.** There is no shared or public board.
   The user id comes from `AuthBloc.state` at shell mount time.

2. **A location is identified by its zone, not by its city.** Adding "Sao Paulo"
   and then "Rio de Janeiro" (both `America/Sao_Paulo`) is **rejected** with a
   `DuplicateZoneFailure` that names the existing row. Two rows showing identical
   times is noise, and the grid has no way to distinguish them.

3. **Home is a zone id, not a board row.** `homeZoneId` is the reference every
   relative offset is measured against. It may or may not also appear in
   `locations`. On first sign-in it is seeded from `deviceZoneId()`; when that
   falls back to UTC, the user is prompted to pick a home city.

4. **The board caps at 20 locations.** Beyond that the grid stops being readable
   and the ticker cost stops being trivial. Adding a 21st returns
   `BoardFullFailure`. The cap is a constant in
   `lib/features/locations/domain/board_limits.dart`, not a scattered literal.

5. **Order is user-controlled and explicit.** `sortIndex` is dense and 0-based.
   Reordering rewrites the indices of the affected range in one write, never one
   write per row.

6. **An empty board is a valid state**, not an error. Every consumer renders
   `FeatureEmptyState` with an "add your first city" CTA. The grid does not crash
   on zero rows, and the world clock shows only the home clock.

7. **Removing a location is immediate and undoable via snackbar** for 5 seconds.
   No confirmation dialog: the action is cheap to reverse and a dialog per
   removal is friction on the app's most common edit.

8. **Removing the home zone's row does not clear `homeZoneId`.** They are
   independent (rule 3). The relative offsets keep working.

9. **Search matches on name, local name, country and aliases**, accent- and
   case-insensitively, through `normalizeForSearch()`
   (`lib/core/utils/string_normalize.dart`). Ranking is: exact name match, then
   prefix match, then substring match; ties break by descending `population`.
   "sao paulo", "SAO PAULO" and "são paulo" must all find the same city.

10. **Search also accepts a raw IANA id.** Typing `Asia/Tokyo` finds Tokyo. Power
    users and pasted values should not dead-end.

11. **A location whose zone no longer resolves is kept and flagged**, never
    silently dropped. `BoardCubit` marks it `isUnresolved` and the UI renders it
    greyed with a "zone unavailable" note and a replace action. Dropping rows on
    a tzdata upgrade would delete user data without consent.

12. **The catalog is never the source of truth for a saved row.** After a catalog
    regeneration, existing boards keep their stored `label`. Only an explicit
    edit changes it.

## Repository Contract

```dart
abstract class BoardRepository {
  /// Local-first: reads the cached board, then reconciles with the remote one.
  /// See sync.md for the reconciliation rules.
  Future<Either<Failure, BoardEntity>> getBoard({
    required String userId,
    bool forceRefresh = false,
  });

  /// Writes the whole board. There is no per-row endpoint: the document is one
  /// unit under 10 KB and partial writes would need a merge strategy for no gain.
  Future<Either<Failure, BoardEntity>> saveBoard({
    required String userId,
    required BoardEntity board,
  });
}

abstract class CityCatalogRepository {
  /// Loads and parses the asset. Idempotent, cached in memory.
  Future<Either<Failure, List<CityEntity>>> load();

  /// Ranked search. Returns at most [limit] results. See rules 9 and 10.
  Future<Either<Failure, List<CityEntity>>> search(String query, {int limit = 30});
}
```

**Cache strategy:**

- `getBoard(forceRefresh: false)` reads `shared_preferences` only, so the app
  opens with no network wait.
- `getBoard(forceRefresh: true)` fetches Firestore, reconciles by `revision`,
  writes the winner back to both sides.
- `saveBoard` writes local first (so the UI is never waiting on the network),
  then remote. A remote failure leaves a dirty flag for the next sync and is
  **not** surfaced as an error to the user. See [sync.md](sync.md).

## Model Serialization

`BoardModel` extends `BoardEntity`. The same JSON shape is used for
`shared_preferences` and for Firestore, so there is one serializer, not two.

| JSON field | Dart field | Notes |
|---|---|---|
| `homeZoneId` | `homeZoneId` | `String`; missing or unknown degrades to `deviceZoneId()` |
| `locations` | `locations` | `List<Map>`; a malformed entry is skipped, not fatal |
| `revision` | `revision` | `int`; missing degrades to `0` |
| `updatedAt` | `updatedAt` | Firestore `Timestamp` / local ISO-8601 string, both to UTC `DateTime` |

`SavedLocationModel` fields map 1:1. `addedAt` follows the same dual encoding.

**Defensive parsing is mandatory** on both boundaries: a non-map entry, a missing
`zoneId` or a non-int `sortIndex` drops that one row and keeps the rest. The
board is the user's whole state; one bad field must not cost them the list.

## State Machine

### BoardCubit

Session-scoped, created by the shell route with the `userId`.

```dart
sealed class BoardState extends Equatable
BoardInitial
BoardLoading
BoardLoaded({ board: BoardEntity, unresolvedIds: Set<String>, isSyncing: bool })
BoardError({ failure: Failure })
```

**Transitions:**

```
BoardInitial ──load()──────────→ BoardLoading → BoardLoaded(board)   [local hit or remote ok]
                                              → BoardError(failure)   [no local and remote failed]

BoardLoaded ──addLocation(city)──→ BoardLoaded(board + row)          [optimistic, then persist]
                                 → BoardLoaded(board) + snack        [DuplicateZoneFailure / BoardFullFailure]

BoardLoaded ──removeLocation(id)─→ BoardLoaded(board - row)          [optimistic, undo for 5s]
BoardLoaded ──reorder(from, to)──→ BoardLoaded(board reindexed)      [optimistic]
BoardLoaded ──setHome(zoneId)────→ BoardLoaded(board)                [optimistic]
BoardLoaded ──refresh()──────────→ BoardLoaded(isSyncing: true) → BoardLoaded(merged)
```

**Mutations are optimistic.** The state updates first, persistence follows. A
local persistence failure rolls the state back and shows a snackbar; a remote
failure does not (see sync.md). Users reorder cities by dragging, and a row that
snaps back because a write is in flight feels broken.

### LocationSearchCubit

Page-scoped, created by the add-location sheet.

```dart
LocationSearchInitial
LocationSearchLoading
LocationSearchResults({ query: String, cities: List<CityEntity> })
LocationSearchEmpty({ query: String })
```

Debounce is 200 ms. An empty query returns a curated default list (the largest
city per continent) rather than nothing, so the sheet is useful before typing.

## Edge Cases

- **First sign-in, device zone detected** → board is created with `homeZoneId` =
  device zone and an empty `locations` list. The empty state invites the first
  add.
- **First sign-in, device zone detection failed** → `homeZoneId` is `UTC` and the
  UI shows a one-time "pick your home city" prompt instead of the empty state.
- **Adding the home city as a row** → allowed. Users want their own time in the
  grid alongside the others.
- **Adding a second city in the same zone** → rejected, rule 2, with a snackbar
  naming the row that already covers it.
- **Board at the 20-city cap** → the add button stays enabled but the sheet shows
  the cap message on selection, so the user learns why rather than facing a dead
  control.
- **Two devices reorder concurrently** → last write wins by `revision`; see
  [sync.md](sync.md). The losing device's order is overwritten on its next sync.
- **A saved zone id was renamed upstream** → `zoneOrNull` resolves the alias
  (timezone_engine rule 4) and `BoardCubit` rewrites the stored id on the next
  save. Transparent to the user.
- **A saved zone id no longer exists at all** → rule 11: kept, flagged, greyed,
  replaceable.
- **Catalog asset missing or corrupt** → `CityCatalogRepository.load` returns
  `Left(ServerFailure)`; the board still renders from stored labels, and only the
  add-location sheet shows the error. A broken catalog must not take down the app.
- **Search query is a raw zone id with wrong casing** (`asia/tokyo`) → normalized
  and matched, rule 10.

## Firestore

**Document:** `users/{userId}/settings/board`

Fields: `homeZoneId`, `locations[]`, `revision`, `updatedAt`.

Read and written by document id only. No composite indexes.

## Testing

`test/features/locations/` covers:

- `BoardCubit`: load from local, load from remote, add, duplicate rejection, cap
  rejection, remove and undo, reorder reindexing, `setHome`, optimistic rollback
  on a local write failure.
- `BoardModel`: round-trip serialization, malformed row skipped, missing
  `revision` defaults to 0, `Timestamp` and ISO string both parse.
- `CityCatalogRepository.search`: accent-insensitive match, alias match, raw zone
  id match, population ranking, `limit` respected.
- Unresolved-zone flagging with a zone id the tzdata does not know.

Factories: `aSavedLocation()`, `aBoard()`, `aCity()` in
`test/harness/factories/`.
