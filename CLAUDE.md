# TimeBuddy: Project Conventions

Real-time world clock and timezone comparison tool built with Flutter.
Supports Android and Web, with the same account synced across both.

---

## Architecture

**Clean Architecture** with feature-first organization:

```
lib/
├── app/              # App shell: DI, routing, theme, widgets, assets
├── core/             # Shared: time/, storage/, sync/, session/, platform/,
│                     #   errors/, extensions/, utils/
├── features/
│   ├── auth/            # Google sign-in, onboarding, AuthBloc
│   ├── locations/       # City catalog, saved board, search
│   ├── preferences/     # The preferences document and its cubit
│   ├── profile/         # The profile page
│   ├── settings/        # The settings page
│   ├── startup/         # The splash gate and StartupCubit
│   ├── time_converter/  # ConvertTimeUseCase and the converter page
│   ├── time_grid/       # BuildGridUseCase and the comparison grid
│   └── world_clock/     # BuildWorldClockUseCase and the live clock list
└── gen/              # Generated code (i18n)

scripts/              # build_city_catalog.dart + city_seeds.dart +
                      #   check_glyphs.py (build tooling, not shipped)
site/                 # The landing page at the Pages root: Vite + Tailwind,
                      #   its own toolchain, deployed by the same workflow
```

Each feature follows:

* `domain/`: entities, repository interfaces, use cases
* `data/`: models, datasources, repository implementations
* `presentation/`: cubits/blocs, pages, widgets

Three modules are presentation only, and deliberately so. `settings/` is a
screen over the preferences feature's entity, repository and cubit, and giving
it a `domain/` of its own would be a second owner of the same document;
`profile/` is a screen over `auth` and the sync status; `startup/` is a cubit
that composes four collaborators it does not own. Sync itself lives in
`core/sync/` rather than in a feature: it is the one place that reconciles
*both* documents against one account, and a copy of the conflict rules per
feature would be two owners of one rule.

## Code Style

* Functions: 5–25 lines. Split if longer.
* Files: ideally under 400–600 lines.
* One responsibility per function/module (SRP).
* Prefer small, composable widgets over large ones.

### Naming

* Names must be specific and intention-revealing.
* Avoid generic names like `data`, `manager`, `handler`.
* Prefer names that are searchable and unique within the codebase.
* Time-related names must say **which** time: `utcInstant`, `localTimeAt`,
  `referenceHour`, `zoneId`. A bare `time` or `date` is a bug waiting to happen
  in an app whose whole domain is "the same instant seen from N places".

### Control Flow

* Prefer early returns over nested conditionals.
* Maximum 2 levels of indentation.

---

## Comments

* Write **WHY**, not WHAT.
* Preserve important context and decisions.
* Do not remove meaningful comments during refactors.
* Public APIs must include:

  * intent
  * parameters
  * usage example

## Key Technologies

| Aspect               | Detail                                                                          |
| -------------------- | ------------------------------------------------------------------------------- |
| **State management** | flutter_bloc (Cubits for simple state, Blocs for event-driven)                  |
| **DI**               | get_it (service locator in `lib/app/di/injection_container.dart`)               |
| **Routing**          | go_router (declarative; hash URLs on web). `StatefulShellRoute.indexedStack`, one branch per destination, so each keeps its own navigator and scroll position |
| **Timezone engine**  | `timezone` package (IANA tzdata) + `flutter_timezone` for device zone detection |
| **Local storage**    | `shared_preferences` holding two JSON documents (preferences and board), the two dirty flags that remember an unpushed write, and the guest marker. No SQL, no ORM. |
| **Remote sync**      | Firebase Firestore (`users/{userId}/settings/*`), last-write-wins by revision |
| **Auth**             | Firebase Auth + Google Sign-In (Google only, no email/password) |
| **Error handling**   | dartz Either<Failure, T> pattern (the UI switches on the failure *type* to pick a localized string; `Failure.message` is for logs) |
| **Linting**          | very_good_analysis (strict). Four rules are turned off in `analysis_options.yaml`; only `prefer_initializing_formals` carries its reason above it, and the other three (`public_member_api_docs`, `sort_pub_dependencies`, `document_ignores`) are bare lines that should each grow one |
| **i18n**             | slang (generated in `lib/gen/`), pt-BR and en                                   |
| **Theme**            | Light + Dark Material 3, custom AppColors / AppTheme, 10 + 10 palettes          |
| **City catalog**     | Static asset JSON (`lib/app/assets/data/cities.json`): 500 cities, generated by `scripts/build_city_catalog.dart` from the shipped tzdata plus a curated seed table. Parsed once and cached in memory; there is no catalog API call. |

> **Why no local database.** The entire persisted state is one list of saved
> locations plus a preferences map, both under 10 KB, always read whole and never
> queried by field. A relational cache would add a codegen step, a migration
> surface and a web WASM worker for zero benefit.
> See [docs/specs/sync.md](docs/specs/sync.md).

## Commands

```bash
flutter test                             # Run all tests
flutter test test/core/time/             # Run one folder's tests
flutter analyze                          # Static analysis (zero issues)
flutter run -d chrome                    # Run the web build
flutter run                              # Run on the connected Android device
dart run slang                           # Generate i18n
dart run scripts/build_city_catalog.dart # Regenerate the city catalog asset

flutter build web --release --no-tree-shake-icons  # Release web bundle
python scripts/check_glyphs.py                     # Verify the icon glyphs survived

npm --prefix site ci                     # Landing site: install (first time)
npm --prefix site run dev                # Landing site: local preview
npm --prefix site run build              # Landing site: static output -> site/dist
npm --prefix site run typecheck          # Landing site: its only test
```

**On Git Bash for Windows, a `--base-href` starting with `/` is rewritten into
a Windows path** by MSYS before Flutter sees it, and the build stops with
`Received a --base-href value of "C:/Program Files/Git/timebuddy/app/"`. Use
PowerShell for that one flag, or prefix the command with `MSYS_NO_PATHCONV=1`.
CI runs on Linux and never meets it.

**`--no-tree-shake-icons` is not optional.** The icon tree-shaker scans the
compiled constants for `IconData` and rewrites each bundled font to hold only
the code points it found; `font_awesome_flutter` wraps every glyph in a
`FaIconData`, which the shaker cannot see through, so a release build keeps a
fraction of the icons and silently drops the rest as empty boxes. A missing
glyph is not a build error, which is why `check_glyphs.py` exists: it parses
each bundled font's `cmap` and compares it against every `FontAwesomeIcons.*`
in the source. Run it after any change that adds, removes or swaps an icon. CI
(`.github/workflows/deploy-pages.yml`) runs the same two commands, adding
`--base-href /timebuddy/app/` to the build because a project page is not served
from the domain root **and the app no longer sits at the project root** — the
landing site does, with the app one level down.

**The published site is two bundles in one deployment.** `site/` is a Vite +
Tailwind static page built by the same workflow job, and the job assembles
`site/dist` at the root of the Pages artifact with `build/web` under `app/`. One
job rather than two, because a Pages deployment carries exactly one artifact and
two jobs racing to publish would leave a site pointing at an app that had not
landed. Old app bookmarks (`/timebuddy/#/settings`) still work: the landing page
forwards any hash beginning with `#/` to `./app/`.

slang is the only code generator this project runs, and it is invoked directly
rather than through `build_runner`: one generator with its own CLI does not need
a build graph on top of it. `slang_build_runner` and `build_runner` are
nonetheless still in `dev_dependencies` with no `build.yaml` and no call site;
they are leftovers from the scaffold, not a second path.

`build_city_catalog.dart` rewrites `lib/app/assets/data/cities.json` from the
zones the app actually ships plus the curated seeds in `scripts/city_seeds.dart`
([docs/specs/locations.md](docs/specs/locations.md)). It is offline and
deterministic (rows sorted, JSON keys in a fixed order, nothing about the
current time in the output), so a run that changed no input produces an empty
diff, and any diff is therefore a real change worth reading. It resolves every
id through `zoneOrNull` and aborts on a miss rather than emitting a city whose
clock would silently fall back to UTC.

## Post-Change Checklist

After every code change:

1. Run `dart run slang` if any i18n JSON was modified
2. Run `dart run scripts/build_city_catalog.dart` if `scripts/city_seeds.dart`
   or the zone-to-country tables in the script changed, and commit the
   regenerated asset with them
3. Run `flutter analyze`: **zero** errors, warnings, and info-level issues
4. Run `flutter test`: all tests must pass. Two suites are worth knowing about
   before you touch what they cover, because both assert properties that are
   easy to break without noticing:
   `test/app/theme/palette_contrast_test.dart` measures every colour pair the
   app paints against WCAG AA on all twenty palettes, and
   `test/app/accessibility_test.dart` asserts that every icon-only control has
   a name and that an hour cell says which band it is in
4b. Run `npm --prefix site run typecheck` if anything under `site/` changed
5. If the change added, removed or swapped an icon, build the web bundle and
   run `python scripts/check_glyphs.py`: a dropped glyph fails neither the
   analyzer nor the tests, and only shows up as an empty box on screen
6. Update the affected spec in `docs/specs/` if behavior changed
7. Never add `// ignore` without clear justification. `lib/` currently holds
   exactly three hand-written ones, each with its reason in the line above it:
   * `lib/core/time/clock.dart`: `one_member_abstracts`, because the type
     exists to be swapped for a fake, which a top-level function cannot be
   * `lib/core/sync/sync_coordinator.dart`: `use_setters_to_change_properties`
     on `startSession`, because a setter would drop the named argument and an
     account id at a call site should say whose it is, and because it pairs
     with `endSession()`
   * `lib/features/locations/data/repositories/city_catalog_repository_impl.dart`:
     `avoid_catching_errors`, because a missing or misdeclared asset arrives as
     a `FlutterError` — an `Error`, not an `Exception` — and letting it through
     would crash the whole app over one broken asset, which the spec forbids

   (`lib/gen/` and `lib/firebase_options.dart` carry `ignore_for_file` headers
   too, but those are written by slang and `flutterfire configure`; they are
   not ours to add to or remove.)

## Spec-Driven Development

Every feature MUST have a spec at `docs/specs/<feature>.md` before writing new
code or tests.

### Workflow

1. Write or update the spec (business rules, contracts, state machines)
2. Write tests based on the spec
3. Implement or modify code to pass the tests
4. Update the spec if requirements change

### Spec Structure

* Entity contract (fields, types, invariants)
* Business rules (numbered, testable)
* Repository contract (methods, parameters, return types)
* State machines (cubit/bloc states and transitions)
* Edge cases

## Time & Timezone Rules

This is the project's highest-risk area. Every rule below exists because the
naive version silently produces a wrong hour for some user, some month a year.

1. **Store and pass instants in UTC.** A `DateTime` crossing a layer boundary is
   UTC unless its name says otherwise. Convert to a zone only at the point of
   display or of an explicit domain calculation.
2. **Never store or cache a numeric offset.** An offset is a function of
   `(zone, instant)`, not of a zone. Sao Paulo is `-03:00` today and could be
   `-02:00` under a future DST rule for a meeting three months out. Always
   resolve through the engine for **the instant in question**.
3. **Never do timezone math with `DateTime.add` on a local time.** Adding 24
   hours across a DST transition gives 23 or 25 real hours. Build the target
   `TZDateTime` from its calendar fields instead.
4. **Never call `DateTime.now()` in `lib/`.** Inject `Clock`
   (`lib/core/time/clock.dart`). Every state in this app is a function of "now",
   so a hardcoded now is an untestable feature.
5. **Never call `tz.getLocation(id)` directly at a persistence boundary.** It
   throws on an unknown id, so one stale saved row crashes the whole board. Use
   `zoneOrNull(id)` and handle the `null`: an id that does not resolve is kept
   and flagged, never silently swapped for another zone
   ([docs/specs/locations.md](docs/specs/locations.md) rule 11).
6. **Offsets are not whole hours.** India is `+05:30`, Nepal `+05:45`, Chatham
   `+12:45`. Any layout that assumes every row aligns to whole-hour columns is
   wrong. See [docs/specs/time_grid.md](docs/specs/time_grid.md).
7. **A day is not always 24 hours.** On DST transition days it is 23 or 25.
   Grid and converter derive their column count from the engine, never from
   the constant 24.
8. **Import `data/latest_all.dart`, never `data/latest.dart`.** `latest.dart`,
   the obvious import, loads **341** locations and drops every IANA `Link`
   line; `latest_all.dart` keeps them, for **598** names and 185 KB more
   bundle, which is nothing beside CanvasKit.

   **This rule used to claim more than it could deliver, and the correction is
   worth keeping.** It said an unresolved `Europe/Oslo` would fall back to UTC
   and read one hour wrong for half the year. It does not. Rule 9's alias map
   is consulted *before* the direct lookup and folds Oslo onto `Europe/Berlin`,
   Kuala Lumpur onto `Asia/Singapore`, Accra onto `Africa/Abidjan` — the same
   clock in every case, because that is what a `Link` line means. Run the whole
   shipped catalog through `zoneOrNull` against both datasets and the answers
   are identical for **312 of its 313** distinct zone ids.

   The one that differs is `Asia/Choibalsan`, a `Link` the alias map does not
   carry: under `latest.dart` it resolves to nothing and the board flags that
   row unresolved (locations rule 11) rather than showing a wrong hour. So the
   real case for `latest_all` is not a cliff — it is one city today, plus not
   depending on a hand-maintained map of roughly 250 entries to stay complete
   as upstream adds `Link` lines. That is still worth 185 KB; it is just a
   different argument, and pinned by `test/core/time/tzdata_dataset_test.dart`,
   which is the only test file in the suite that may not call
   `initTestTimeZones()`. See
   [docs/specs/timezone_engine.md](docs/specs/timezone_engine.md) rule 4.
9. **Every zone id still goes through `zoneOrNull`.** The dataset
   removes the cliff, not the need: ids arrive from platform APIs, public city
   datasets and old storage, and the lookup is also what canonicalises a `Link`
   onto its target, so two spellings of one clock cannot become two board rows.
   Verify a new id against `tz.timeZoneDatabase.locations`, never against the
   IANA list.

## Testing Rules

* Every new use case must have tests
* Every bug fix must include a regression test
* Every timezone rule above must have at least one test pinning a real historical
  or scheduled transition, not a synthetic zone
* Tests must follow F.I.R.S.T principles:

  * Fast
  * Independent
  * Repeatable
  * Self-validating
  * Timely

### Test Structure

* One test file per source file (mirrors `lib/`)
* Use `bloc_test` for cubit/bloc testing
* Use factories for test data, never hardcode entities
* Mock at boundaries:

  * repositories for cubits
  * datasources for repositories
* Time is **always** injected via a `FakeClock`. A test that reads the real wall
  clock is a flaky test that fails once a year at 02:00.

---

## Harness Engineering

Test infrastructure lives in `test/harness/`:

* `mocks.dart`: centralized mock declarations (mocktail)
* `helpers.dart`: shared test setup and utilities
* `fake_clock.dart`: the deterministic clock every time-dependent test uses
* `pump_app.dart`: the widget-test entry point. Every page test mounts through
  `pumpApp`, which stands up the four things a page needs at once (the service
  locator, a loaded `PreferencesCubit`, slang's `t`, the theme) and owns the
  two globals a widget test otherwise leaks: `GetIt` and the `TickerService`
  timer. Standing that up inline is thirty lines per test and thirty chances to
  assert on a tree the app never builds
* `factories/`: test data factories per entity

`helpers.dart` exposes `initTestTimeZones()`, which loads the tzdata once per
test run. Any test touching the engine must call it in `setUpAll`.

## Dependencies

* Depend on abstractions, not implementations
* Inject dependencies via constructor or DI
* External libraries must be wrapped behind project-owned interfaces.
  In particular, the `timezone` package is importable **only** from
  `lib/core/time/`. Features talk to `TimeZoneEngine`, never to `tz.*`.

## Code Conventions

* Entities use `Equatable` and provide `copyWith`
* Failures are sealed classes (`ServerFailure`, `AuthFailure`, etc.)
* Use cases are single-method classes with `call()` operator
* Models extend entities and handle serialization
* All repository methods return `Future<Either<Failure, T>>`
* Use package imports (`package:timebuddy/...`)
* Apply `const` constructors wherever possible

### Shared helpers: reach for these instead of re-rolling

| Helper | Where | Use it for |
| ------ | ----- | ---------- |
| `Clock` / `clock.nowUtc()` | `lib/core/time/clock.dart` | Reading the current instant. **Never `DateTime.now()`** in `lib/`: it makes every downstream widget untestable and hides DST bugs behind "it worked when I ran it". |
| `zoneOrNull(id)` | `lib/core/time/zone_lookup.dart` | Resolving a persisted IANA id, and the only sanctioned way to do it. `tz.getLocation` throws on an unknown or renamed id (`Asia/Calcutta` became `Asia/Kolkata`), so one stale row would crash the board; and the alias map is what folds a `Link` onto its target, so `Europe/Oslo` and `Europe/Berlin` cannot become two rows of one clock (rule 9). It hands back a `ZoneRef` carrying the canonical `id`, the `requestedId` and `wasAliased`. **Nothing in `lib/` reads those last two yet**: the intent was that a caller rewrite a stale row instead of paying for the same alias lookup on every launch, and no caller does. They are kept because the information is free at the point it is known and impossible to recover later. `zoneOrHome(id, home)` used to sit beside this and was **deleted**: it substituted the home zone for an unresolved id, which [docs/specs/locations.md](docs/specs/locations.md) rule 11 forbids — an unresolved row is kept and flagged, never quietly replaced by a clock that reads as plausible and is someone else's. |
| `utcZoneId` | `lib/core/time/zone_lookup.dart` | The one fallback id, and the literal to compare a zone against. It is the short `'UTC'` rather than `'Etc/UTC'` because that is what gets persisted and shown to a user. `latest_all` does register the short name, but the lookup still wires it to `tz.UTC` by hand, so the one id the app persists cannot be taken away by a future dataset change. |
| `TimeZoneEngine` | `lib/core/time/timezone_engine.dart` | Every conversion, offset and DST question. The only place in `lib/` allowed to import `package:timezone`. |
| `TickerService` | `lib/core/time/ticker_service.dart` | Anything that has to update as the clock advances. One broadcast stream for the whole app (see Performance). |
| `hourBandFor(localHour, workingHours)` | `lib/core/time/hour_band.dart` | Deciding how reachable an hour is. Derived from the current preferences on every read and never stored on an entity: a cached band outlives the working window that produced it. |
| `WorkingHours` | `lib/core/time/working_hours.dart` | The working window itself. Half-open and wrap-aware, so a `22:00-06:00` night shift is an ordinary value and no caller special-cases midnight; `clamped()` is the one sanctioned repair for a window that came back invalid from storage. |
| `offsetLabel(offset)` | `lib/core/utils/time_formatter.dart` | Rendering `+05:30` / `-03:00`. Handles the sign, the padding and the non-whole-hour minutes that a naive `${h}h` string gets wrong. |
| `relativeOffsetLabel(offset)` | `lib/core/utils/time_formatter.dart` | Rendering a zone-to-zone difference as `+4h` / `-3h30`. Returns `null` on a zero difference, because a row that matches home should show no badge at all: the absence is the information. |
| `formatClock(localTime, format, {showSeconds})` | `lib/core/utils/time_formatter.dart` | Rendering a wall-clock time under the user's 12h/24h preference. `localTime` must already be wall-clock time in the zone being shown: the function reads calendar fields verbatim and cannot tell a converted value from a raw UTC instant, so passing one prints a plausible hour that is wrong for every zone but UTC. |
| `formatGridHour(localTime)` | `lib/core/utils/time_formatter.dart` | Rendering an hour in the time grid — its cells and its header ruler, and nothing else. The grid is **always 24h, by design**, so this one place ignores the user's hour-format preference: a 24-column ruler in 12h prints `03` twice with nowhere in a 48-60pt column to put the am/pm that would tell them apart. Everywhere outside the grid, `formatClock` and the preference win. |
| `formatDayMonth(localTime, localeTag)` | `lib/core/utils/time_formatter.dart` | Rendering the `Tue 24` date label of a row. Per row, never once per screen: at a single instant two cities can be on different calendar dates. |
| `normalizeForSearch(input)` | `lib/core/utils/string_normalize.dart` | Folding a catalog entry or a typed query into the one index key both share: lower-case, diacritic-free, single-spaced. Both sides are folded, so `Sao Paulo` and the accented spelling are the same query. Never fold a value that will be stored or displayed; this is a lossy key, not a label. |
| `enumByNameOrNull(values, raw)` / `enumByName(values, raw, orElse: ...)` | `lib/core/utils/enum_parse.dart` | Parsing an enum from a persisted `enum.name`. **Never `Values.byName`** at a Firestore/JSON boundary: it throws on an unknown value, turning one bad field into a crashed screen. |
| `filledStringOrNull(raw)` / `intOrNull(raw)` / `timestampFromJson(raw)` | `lib/core/utils/json_parse.dart` | Reading an untyped field out of a persisted document. Each one degrades instead of throwing, which is the whole contract at a JSON/Firestore boundary: one bad field must not crash a screen. `filledStringOrNull` also trims, so a stored `" dark "` is still the value the user picked. **Never `as String` / `as int` on decoded JSON** — these four coercions existed as eleven private copies under six names across five models before they were folded here. |
| `guardStorage(body)` | `lib/core/utils/storage_guard.dart` | Wrapping a repository method that touches the device store. Turns `CacheException` and `StorageException` into `Left(StorageFailure(...))` in one place; the ladder was written out four times across the two repositories, and four copies of one `catch` is four chances to catch a different set. |
| `store.readJsonObject(key, malformedMessage:)` | `lib/core/storage/local_store.dart` | Reading a stored JSON document. An extension rather than a member of `LocalStore` on purpose: the interface is implemented by test doubles, and Dart's `implements` would force every one of them to reimplement a method none of them cares about. |
| `LocalStore` / `StorageKeys` | `lib/core/storage/local_store.dart` | Every read and write to the device store. Keys are declared once, and the three that hold a **document** (`board.v1`, `preferences.v1`, `guest.v1`) carry a version suffix, so a breaking change to a JSON shape writes `.v2` and leaves behind a document an older build can still parse. The two dirty flags (`dirty.board`, `dirty.preferences`) deliberately do not: a bool meaning "this document still owes the server a write" has no shape to break, and versioning it would strand a pending write behind a rename. |
| `context.appColors` | `lib/core/extensions/context_extensions.dart` | Reading a semantic color token. Never `AppColors.light` / `AppColors.dark` at a call site: naming one hardcodes a brightness that survives a theme switch and only shows up in the other mode. |
| `colors.primaryInk` / `primaryGlyph` / `warningInk` / `successInk` / `errorInk` | `lib/app/theme/app_colors.dart` | Drawing an accent **as content** — accent text, a marker, a status icon. The catalog picks its colors to be *fills*, and six of the ten light palettes then fail as content: Mint Fresh's `primary` is 2.39:1 against its own page. Each getter is `inkFor(token)`, which returns the token untouched when it already clears the bar and otherwise pulls it 40% toward `onBackground`, so 13 of the 20 palettes are not repaired at all. Keep raw `primary` / `warning` for the fill, the disc and the wash. |
| `contrastRatio(a, b)` | `lib/app/theme/app_colors.dart` | Measuring two **opaque** colors. Composite a translucent one first (`Color.alphaBlend`) — the formula has nowhere to put an alpha and will happily report a ratio for a color nobody sees. `AppColorsData.minTextRatio` (4.5) and `minGlyphRatio` (3.0) are the two bars. |
| `context.popOrGo(fallbackRoute, {result})` | `lib/core/extensions/context_navigation_extensions.dart` | Closing a pushed sub-page. Every sub-page is URL-reachable on web, so a deep-linked route has an empty stack and a bare `pop()` strands the user on web and closes the app on Android. Reached through `TimeBuddyLargeAppBar`: pass it a `fallbackRoute` and its back chevron renders even when there is nothing to pop, closing through `popOrGo` instead of `Navigator.pop`. Without one the bar keeps its older rule and hides the chevron rather than drawing a dead control. |
| `context.showSnack(message)` | `lib/core/extensions/context_extensions.dart` | Plain-text feedback. Snackbars needing actions or custom durations still call `ScaffoldMessenger` directly. |
| `bottomSafeForFab(context, isSubPage:)` / `bottomSafeForBar(context, isSubPage:)` | `lib/app/widgets/fab_safe_area.dart` | Bottom padding of any scroll view on a page that has chrome floating over it. The bar and the FAB reserve no layout space, so a list that stops at its own last pixel hands the user a final row they can see and cannot tap. Both derive their numbers from `TimeBuddyBottomBar.reservedHeight` and `kFloatingActionButtonMargin`, so a per-page `120` invented at a call site drifts the moment the bar is retuned. |
| `ResponsiveLayout.isMobile` / `.showsSidebar` / `.sidebarIsExpanded` / `.maxContentWidth` | `lib/app/widgets/responsive_layout.dart` | Every breakpoint question. There are **two** numbers now, not one: `mobileBreakpoint` 600, below which the floating bottom bar replaces the rail, and `desktopBreakpoint` 900, above which the rail shows its labels instead of icons. Ask the right one — `isMobile` means "is this a phone", `showsSidebar` means "is the rail on screen at all" (the FAB lift, both clearance helpers and the snackbar mean its inverse), `sidebarIsExpanded` means "is the rail wide enough to own the date stepper". Those were one question until the rail grew a collapsed form. `maxContentWidth` survives with exactly one call site, onboarding, which is prose; the row-and-list screens were uncapped deliberately (see the roadmap's Financo design pass). |
| `LiftedFab` | `lib/app/widgets/lifted_fab.dart` | Wrapping anything handed to `Scaffold.floatingActionButton`. It lifts only when the bottom bar is actually on screen (mobile, sub-page depth 0), which the page itself cannot know, since the sub-page that hides the bar is pushed *above* it. |
| `SubPageScope` / `subPageDepth` | `lib/app/widgets/sub_page_scope.dart` | Marking a pushed sub-page, and asking whether one is open. The chrome that reacts (bar, date pill, FAB lift) is built above the pushed route, so an `InheritedWidget` would flow the wrong way. Only `SubPageScope` writes the counter. |
| `ShellDatePill` | `lib/app/routes/app_shell.dart` | Placing a page's reference-day stepper. It renders in place unless the rail is *expanded* (`sidebarIsExpanded`, so 900 and up), because an 80pt icon rail cannot hold a stepper and hands it back; a page that implements half of that rule shows two steppers on a tablet. |

### UI & Formatting

* Every user-facing string via slang (`t.section.key`), never hardcode
* Times rendered with `formatClock()` and offsets with `offsetLabel()`, never
  with an inline `DateFormat` or string interpolation. The one exception is the
  time grid, whose hour cells and header ruler go through `formatGridHour()`:
  the grid is always 24h by design, for the reason on that helper's row above
* Zone display names come from the location catalog, never from the raw IANA id.
  `America/Sao_Paulo` is an identifier; "Sao Paulo" is a label

## State Management

* **Bloc** for complex event-driven logic (Auth)
* **Cubit** for everything else (Board, Grid, WorldClock, Converter,
  Preferences, Startup). Theme mode, both palettes and the locale tag are fields
  of Preferences, not cubits of their own

### Rules

* UI must not contain business logic
* Cubits/Blocs orchestrate, UseCases execute logic
* State must be immutable

### Lifecycle

* Session-independent services and cubits are singletons. **Every registration
  in `lib/app/di/injection_container.dart` is a `registerLazySingleton`; there
  is not one factory in the graph.** In registration order: `Clock`,
  `LocalStore`, `GuestSession`, `TimeZoneEngine`, `TickerService`, `Uuid`,
  `PreferencesLocalDataSource`, `SyncCoordinator`, `PreferencesRepository`,
  `PreferencesCubit`, `BoardLocalDataSource`, `BoardRepository`,
  `CityCatalogRepository`, `BuildGridUseCase`, `BuildWorldClockUseCase`,
  `ConvertTimeUseCase`, the three Firebase handles (`FirebaseAuth`,
  `FirebaseFirestore`, `GoogleSignIn`), `AppPlatform`, `AuthRemoteDataSource`,
  `AuthRepository`, `AuthBloc`, `RemoteSettingsDataSource`, `SyncService` and
  `StartupCubit`. The reasons that are not "it is stateless" are worth knowing:
  `GuestSession` is the device's one answer to "may this visitor use the app
  without an account", and a second copy would be a second answer;
  `SyncCoordinator` holds the signed-in account id as its state, so a factory
  would hand every repository a permanently signed-out copy and ordinary edits
  would stop pushing without anything failing loudly; `SyncService`'s status
  stream replays its last value, which a per-call instance could not remember;
  `AuthBloc` subscribes to `authStateChanges` in its constructor and is the
  app's only answer to "who is signed in", read by the router redirect, the
  startup cubit and the profile page alike; `StartupCubit` is read by the same
  redirect to decide whether anything but the splash may render;
  `CityCatalogRepository` is a singleton because the parsed catalog *is* the
  cache, and a factory would re-read a 500-row asset on every keystroke in the
  city picker; `BuildGridUseCase`, `BuildWorldClockUseCase` and
  `ConvertTimeUseCase` are pure and stateless, so one instance costs nothing
  and saves their cubits from building one per rebuild; the Firebase handles
  are registered rather than read statically so a data source takes them as
  arguments and a test can hand it fakes, and they resolve lazily, which is
  what lets `main` finish `Firebase.initializeApp` before anything touches
  `.instance`; `AppPlatform` is asked one question — "is this a browser?" — by
  the two auth paths that fork on it, because a `kIsWeb` at those call sites
  would make the web half unreachable from any test; and `Uuid` is registered
  rather than called statically so a test can hand `BoardCubit` a counter and
  assert on the ids it wrote.
* `PreferencesCubit` is the **single source of truth for theme mode, both
  palettes and the locale tag**. There is deliberately no `ThemeCubit`,
  `LightPaletteCubit`, `DarkPaletteCubit` or `AppLocaleCubit`: those are fields
  of one synced document, and two cubits persisting the same field are two
  sources of truth for it, which is one bad merge away from silently resetting a
  palette the user chose. `app_widget` reads the preferences state, reassigns
  `AppColors.light` / `AppColors.dark`, and only then builds `MaterialApp`.
* `BoardCubit` is session-scoped: `AppShell` creates it through `BlocProvider`
  and starts its load, so it lives exactly as long as the shell and is
  deliberately **not** in `GetIt`, where a stray `sl<BoardCubit>()` could hand
  out a second board. The shell rather than a page, because it is the only
  widget that is an ancestor of every page reading the board *and* is built once
  per session: loading in the grid page would re-run on every visit and leave
  the locations page loading the same document a second time, which is two
  answers to "is the board ready". It still takes no `userId`, and that is the
  design rather than an omission: the account never reaches the board cubit at
  all. `SyncService` reconciles the board document during startup, and the
  router only builds `AppShell` once startup has left `/startup`, so the load
  reads an already-reconciled document and there is nothing for a `userId` here
  to decide. (`PreferencesCubit` needs the other half of that arrangement — it
  is a singleton loaded before the router exists, so `StartupCubit` hands it
  the reconciled copy through `adoptFromSync` rather than letting its
  in-memory state outlive the sync that replaced the document.)
* Page-scoped cubits are created per visit by their page and disposed with it:
  `TimeGridCubit` by `TimeGridPage`, `WorldClockCubit` by `WorldClockPage`,
  `TimeConverterCubit` by `TimeConverterPage`, `LocationSearchCubit` by the
  add-location sheet. They read `BoardCubit` and `PreferencesCubit` and own
  only view state (reference date, cursor, query); every board mutation goes
  back through `BoardCubit`, so there is one owner of the list of places.

## Performance

* **One ticker for the whole app.** `TickerService`
  (`lib/core/time/ticker_service.dart`) exposes a single broadcast
  `Stream<DateTime>` at 1 Hz. A `Timer.periodic` per clock tile means N timers
  and N full rebuilds per second on a page that may list 30 cities.
* The ticker drops to 1/60 Hz when no visible widget needs seconds, and pauses
  entirely when the app is backgrounded (`AppLifecycleState.paused`).
* Rebuild only the leaf that shows the time. A clock row is a `StreamBuilder`
  around the digits, not around the row.
* Avoid unnecessary rebuilds (use `const`, selectors, split widgets)
* Lists must use lazy builders (`ListView.builder`, etc.)
* The grid is a two-axis scroll view with a pinned first column; it must not
  build every column of every row eagerly
* Avoid heavy work on the UI thread. The city catalog (500 entries) is parsed
  once and kept in memory, pre-folded into its search keys so a keystroke walks
  strings that are already index keys. `main` does not touch it: it is loaded
  by `StartupCubit._prepare`, started in parallel with tzdata and then awaited.
  `main` runs before there is a screen to report a failure on, which is why
  nothing that can fail lives there.

  **Awaited, but not gated on, and that is a correction.** A catalog failure
  used to be fatal. On web the asset is an HTTP request, so one blip on it was
  showing "TimeBuddy could not start" to a user whose board renders from the
  labels it stored at add time — while
  [docs/specs/locations.md](docs/specs/locations.md) said in as many words that
  a broken catalog must not take down the app. Only tzdata stops the app now.
  Two details keep the recovery real, and both are easy to undo by accident:
  the read passes **`cache: false`**, because `rootBundle` is a
  `CachingAssetBundle` whose `loadString` memoizes a *failed* future forever and
  would hand every later attempt the same error without touching the network;
  and one cold read **fetches twice**, 300 ms apart, so a single blip never
  reaches the user at all

## Firestore Rules

```
users/{userId}
users/{userId}/settings/board
users/{userId}/settings/preferences
```

### Guidelines

* A user can read and write only their own `users/{userId}` subtree. There is no
  cross-user read path and no public collection.
* Reads are by document id only. No queries, no indexes, no unbounded scans.
* The whole remote state is 2 documents per user, so a full sync is 2 reads.

## Firebase: Firestore Collections

```
users/{userId}                       → name, email, photoUrl, createdAt
users/{userId}/settings/board        → homeZoneId, locations[], revision, updatedAt
users/{userId}/settings/preferences  → themeMode, lightPalette, darkPalette, hourFormat, weekStartsOn, workingHours { start, end }, showSeconds, locale, revision, updatedAt
```

`locations[]` entry shape:

```
{ id, zoneId, label, countryCode, sortIndex, addedAt }
```

> `zoneId` is the IANA identifier and the only field the engine reads.
> `label` and `countryCode` are display data denormalized from the city catalog
> at save time, so a board still renders if a future catalog drops that city.
