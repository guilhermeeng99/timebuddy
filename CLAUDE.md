# TimeBuddy: Project Conventions

Real-time world clock and timezone comparison tool built with Flutter.
Supports Android and Web, with the same account synced across both.

---

## Architecture

**Clean Architecture** with feature-first organization:

```
lib/
├── app/              # App shell: DI, routing, theme, widgets, assets
├── core/             # Shared: time engine, storage, errors, utils
├── features/
│   ├── locations/    # City catalog, saved board, search
│   ├── preferences/  # The preferences document and its cubit
│   ├── settings/     # The settings page
│   └── time_grid/    # BuildGridUseCase and the comparison grid
└── gen/              # Generated code (i18n)

scripts/              # build_city_catalog.dart + city_seeds.dart (not shipped)
```

Each feature follows:

* `domain/`: entities, repository interfaces, use cases
* `data/`: models, datasources, repository implementations
* `presentation/`: cubits/blocs, pages, widgets

`settings/` is presentation only, and deliberately so: it is a screen over the
preferences feature's entity, repository and cubit, and giving it a `domain/` of
its own would be a second owner of the same document.

---

## Code Style

* Functions: 5–25 lines. Split if longer.
* Files: ideally under 400–600 lines.
* One responsibility per function/module (SRP).
* Prefer small, composable widgets over large ones.

### Naming

* Names must be specific and intention-revealing.
* Avoid generic names like `data`, `manager`, `handler`.
* Prefer names that are searchable and unique within the codebase.
* Time-related names must say **which** time: `utcInstant`, `localTimeAt`,
  `referenceHour`, `zoneId`. A bare `time` or `date` is a bug waiting to happen
  in an app whose whole domain is "the same instant seen from N places".

### Control Flow

* Prefer early returns over nested conditionals.
* Maximum 2 levels of indentation.

---

## Comments

* Write **WHY**, not WHAT.
* Preserve important context and decisions.
* Do not remove meaningful comments during refactors.
* Public APIs must include:

  * intent
  * parameters
  * usage example

## Key Technologies

| Aspect               | Detail                                                                          |
| -------------------- | ------------------------------------------------------------------------------- |
| **State management** | flutter_bloc (Cubits for simple state, Blocs for event-driven)                  |
| **DI**               | get_it (service locator in `lib/app/di/injection_container.dart`)               |
| **Routing**          | go_router (declarative; hash URLs on web). `StatefulShellRoute.indexedStack`, one branch per destination, so each keeps its own navigator and scroll position |
| **Timezone engine**  | `timezone` package (IANA tzdata) + `flutter_timezone` for device zone detection |
| **Local storage**    | `shared_preferences` holding two JSON documents (preferences and board). No SQL, no ORM. |
| **Remote sync**      | Firebase Firestore (`users/{userId}/settings/*`), last-write-wins by revision. Arrives with M3; there is no Firebase dependency in `pubspec.yaml` yet. |
| **Auth**             | Firebase Auth + Google Sign-In (Google only, no email/password). Arrives with M3. |
| **Error handling**   | dartz Either<Failure, T> pattern (the UI switches on the failure *type* to pick a localized string; `Failure.message` is for logs) |
| **Linting**          | very_good_analysis (strict). Four rules are turned off in `analysis_options.yaml`, each with its reason written above it in the file |
| **i18n**             | slang (generated in `lib/gen/`), pt-BR and en                                   |
| **Theme**            | Light + Dark Material 3, custom AppColors / AppTheme, 10 + 10 palettes          |
| **City catalog**     | Static asset JSON (`lib/app/assets/data/cities.json`): 500 cities, generated by `scripts/build_city_catalog.dart` from the shipped tzdata plus a curated seed table. Parsed once and cached in memory; there is no catalog API call. |

> **Why no local database.** The entire persisted state is one list of saved
> locations plus a preferences map, both under 10 KB, always read whole and never
> queried by field. A relational cache would add a codegen step, a migration
> surface and a web WASM worker for zero benefit.
> See [docs/specs/sync.md](docs/specs/sync.md).

## Commands

```bash
flutter test                             # Run all tests
flutter test test/core/time/             # Run one folder's tests
flutter analyze                          # Static analysis (zero issues)
flutter run -d chrome                    # Run the web build
flutter run                              # Run on the connected Android device
dart run slang                           # Generate i18n
dart run scripts/build_city_catalog.dart # Regenerate the city catalog asset
```

slang is the only code generator this project runs, and it is invoked directly
rather than through `build_runner`: one generator with its own CLI does not need
a build graph on top of it.

`build_city_catalog.dart` rewrites `lib/app/assets/data/cities.json` from the
zones the app actually ships plus the curated seeds in `scripts/city_seeds.dart`
([docs/specs/locations.md](docs/specs/locations.md)). It is offline and
deterministic (rows sorted, JSON keys in a fixed order, nothing about the
current time in the output), so a run that changed no input produces an empty
diff, and any diff is therefore a real change worth reading. It resolves every
id through `zoneOrNull` and aborts on a miss rather than emitting a city whose
clock would silently fall back to UTC.

## Post-Change Checklist

After every code change:

1. Run `dart run slang` if any i18n JSON was modified
2. Run `dart run scripts/build_city_catalog.dart` if `scripts/city_seeds.dart`
   or the zone-to-country tables in the script changed, and commit the
   regenerated asset with them
3. Run `flutter analyze`: **zero** errors, warnings, and info-level issues
4. Run `flutter test`: all tests must pass
5. Update the affected spec in `docs/specs/` if behavior changed
6. Never add `// ignore` without clear justification. `lib/` currently holds
   exactly one, on `Clock`: `one_member_abstracts` is suppressed there because
   the type exists to be swapped for a fake, which a top-level function cannot
   be

## Time & Timezone Rules

This is the project's highest-risk area. Every rule below exists because the
naive version silently produces a wrong hour for some user, some month a year.

1. **Store and pass instants in UTC.** A `DateTime` crossing a layer boundary is
   UTC unless its name says otherwise. Convert to a zone only at the point of
   display or of an explicit domain calculation.
2. **Never store or cache a numeric offset.** An offset is a function of
   `(zone, instant)`, not of a zone. Sao Paulo is `-03:00` today and could be
   `-02:00` under a future DST rule for a meeting three months out. Always
   resolve through the engine for **the instant in question**.
3. **Never do timezone math with `DateTime.add` on a local time.** Adding 24
   hours across a DST transition gives 23 or 25 real hours. Build the target
   `TZDateTime` from its calendar fields instead.
4. **Never call `DateTime.now()` in `lib/`.** Inject `Clock`
   (`lib/core/time/clock.dart`). Every state in this app is a function of "now",
   so a hardcoded now is an untestable feature.
5. **Never call `tz.getLocation(id)` directly at a persistence boundary.** It
   throws on an unknown id, so one stale saved row crashes the whole board. Use
   `zoneOrNull(id)` and degrade to the home zone.
6. **Offsets are not whole hours.** India is `+05:30`, Nepal `+05:45`, Chatham
   `+12:45`. Any layout that assumes every row aligns to whole-hour columns is
   wrong. See [docs/specs/time_grid.md](docs/specs/time_grid.md).
7. **A day is not always 24 hours.** On DST transition days it is 23 or 25.
   Grid, converter and planner derive their column count from the engine, never
   from the constant 24.
8. **Import `data/latest_all.dart`, never `data/latest.dart`.** Measured, not
   assumed: `latest.dart`, the obvious import, loads **341** locations and drops
   every IANA `Link` line. `Europe/Oslo`, `Asia/Kuala_Lumpur`, `Africa/Accra`
   and roughly two hundred other perfectly current ids are simply absent from
   it, and so is plain `UTC`. The danger is that the failure is quiet: an
   unresolved Oslo falls back to UTC, and the user reads a clock that is one
   hour wrong for half the year while looking entirely plausible.
   `latest_all.dart` keeps the `Link` lines (**598** names) for 185 KB more
   bundle, which is nothing beside CanvasKit. See
   [docs/specs/timezone_engine.md](docs/specs/timezone_engine.md) rule 4.
9. **Every zone id still goes through `zoneOrNull` / `zoneOrHome`.** The dataset
   removes the cliff, not the need: ids arrive from platform APIs, public city
   datasets and old storage, and the lookup is also what canonicalises a `Link`
   onto its target, so two spellings of one clock cannot become two board rows.
   Verify a new id against `tz.timeZoneDatabase.locations`, never against the
   IANA list.

## Testing Rules

* Every new use case must have tests
* Every bug fix must include a regression test
* Every timezone rule above must have at least one test pinning a real historical
  or scheduled transition, not a synthetic zone
* Tests must follow F.I.R.S.T principles:

  * Fast
  * Independent
  * Repeatable
  * Self-validating
  * Timely

### Test Structure

* One test file per source file (mirrors `lib/`)
* Use `bloc_test` for cubit/bloc testing
* Use factories for test data, never hardcode entities
* Mock at boundaries:

  * repositories for cubits
  * datasources for repositories
* Time is **always** injected via a `FakeClock`. A test that reads the real wall
  clock is a flaky test that fails once a year at 02:00.

---

## Harness Engineering

Test infrastructure lives in `test/harness/`:

* `mocks.dart`: centralized mock declarations (mocktail)
* `helpers.dart`: shared test setup and utilities
* `fake_clock.dart`: the deterministic clock every time-dependent test uses
* `factories/`: test data factories per entity

`helpers.dart` exposes `initTestTimeZones()`, which loads the tzdata once per
test run. Any test touching the engine must call it in `setUpAll`.

---

## Dependencies

* Depend on abstractions, not implementations
* Inject dependencies via constructor or DI
* External libraries must be wrapped behind project-owned interfaces.
  In particular, the `timezone` package is importable **only** from
  `lib/core/time/`. Features talk to `TimeZoneEngine`, never to `tz.*`.

## Code Conventions

* Entities use `Equatable` and provide `copyWith`
* Failures are sealed classes (`ServerFailure`, `AuthFailure`, etc.)
* Use cases are single-method classes with `call()` operator
* Models extend entities and handle serialization
* All repository methods return `Future<Either<Failure, T>>`
* Use package imports (`package:timebuddy/...`)
* Apply `const` constructors wherever possible

### Shared helpers: reach for these instead of re-rolling

| Helper | Where | Use it for |
| ------ | ----- | ---------- |
| `Clock` / `clock.nowUtc()` | `lib/core/time/clock.dart` | Reading the current instant. **Never `DateTime.now()`** in `lib/`: it makes every downstream widget untestable and hides DST bugs behind "it worked when I ran it". |
| `zoneOrNull(id)` / `zoneOrHome(id, home)` | `lib/core/time/zone_lookup.dart` | Resolving a persisted IANA id. Both hand back a `ZoneRef` carrying the canonical `id`, the `requestedId` and `wasAliased`, so a caller can rewrite a stale row instead of paying for the same lookup on every launch. `tz.getLocation` throws on an unknown or renamed id (`Asia/Calcutta` became `Asia/Kolkata`), so one stale row would crash the board; and the alias map is what folds a `Link` onto its target, so `Europe/Oslo` and `Europe/Berlin` cannot become two rows of one clock (rule 9). `zoneOrHome` never returns null; the fallback stays visible at the call site. |
| `utcZoneId` | `lib/core/time/zone_lookup.dart` | The one fallback id, and the literal to compare a zone against. It is the short `'UTC'` rather than `'Etc/UTC'` because that is what gets persisted and shown to a user. `latest_all` does register the short name, but the lookup still wires it to `tz.UTC` by hand, so the one id the app persists cannot be taken away by a future dataset change. |
| `TimeZoneEngine` | `lib/core/time/timezone_engine.dart` | Every conversion, offset and DST question. The only place in `lib/` allowed to import `package:timezone`. |
| `TickerService` | `lib/core/time/ticker_service.dart` | Anything that has to update as the clock advances. One broadcast stream for the whole app (see Performance). |
| `hourBandFor(localHour, workingHours)` | `lib/core/time/hour_band.dart` | Deciding how reachable an hour is. Derived from the current preferences on every read and never stored on an entity: a cached band outlives the working window that produced it. |
| `WorkingHours` | `lib/core/time/working_hours.dart` | The working window itself. Half-open and wrap-aware, so a `22:00-06:00` night shift is an ordinary value and no caller special-cases midnight; `clamped()` is the one sanctioned repair for a window that came back invalid from storage. |
| `offsetLabel(offset)` | `lib/core/utils/time_formatter.dart` | Rendering `+05:30` / `-03:00`. Handles the sign, the padding and the non-whole-hour minutes that a naive `${h}h` string gets wrong. |
| `relativeOffsetLabel(offset)` | `lib/core/utils/time_formatter.dart` | Rendering a zone-to-zone difference as `+4h` / `-3h30`. Returns `null` on a zero difference, because a row that matches home should show no badge at all: the absence is the information. |
| `formatClock(localTime, format, {showSeconds})` | `lib/core/utils/time_formatter.dart` | Rendering a wall-clock time under the user's 12h/24h preference. `localTime` must already be wall-clock time in the zone being shown: the function reads calendar fields verbatim and cannot tell a converted value from a raw UTC instant, so passing one prints a plausible hour that is wrong for every zone but UTC. |
| `formatDayMonth(localTime, localeTag)` | `lib/core/utils/time_formatter.dart` | Rendering the `Tue 24` date label of a row. Per row, never once per screen: at a single instant two cities can be on different calendar dates. |
| `normalizeForSearch(input)` | `lib/core/utils/string_normalize.dart` | Folding a catalog entry or a typed query into the one index key both share: lower-case, diacritic-free, single-spaced. Both sides are folded, so `Sao Paulo` and the accented spelling are the same query. Never fold a value that will be stored or displayed; this is a lossy key, not a label. |
| `enumByNameOrNull(values, raw)` / `enumByName(values, raw, orElse: ...)` | `lib/core/utils/enum_parse.dart` | Parsing an enum from a persisted `enum.name`. **Never `Values.byName`** at a Firestore/JSON boundary: it throws on an unknown value, turning one bad field into a crashed screen. |
| `LocalStore` / `StorageKeys` | `lib/core/storage/local_store.dart` | Every read and write to the device store. Keys are declared once and carry a `.v1` suffix, so a breaking change to a JSON shape writes `.v2` and leaves behind a document an older build can still parse. |
| `context.appColors` | `lib/core/extensions/context_extensions.dart` | Reading a semantic color token. Never `AppColors.light` / `AppColors.dark` at a call site: naming one hardcodes a brightness that survives a theme switch and only shows up in the other mode. |
| `context.popOrGo(fallbackRoute, {result})` | `lib/core/extensions/context_navigation_extensions.dart` | Closing a pushed sub-page. Every sub-page is URL-reachable on web, so a deep-linked route has an empty stack and a bare `pop()` strands the user. |
| `context.showSnack(message)` | `lib/core/extensions/context_extensions.dart` | Plain-text feedback. Snackbars needing actions or custom durations still call `ScaffoldMessenger` directly. |
| `bottomSafeForFab(context, isSubPage:)` / `bottomSafeForBar(context, isSubPage:)` | `lib/app/widgets/fab_safe_area.dart` | Bottom padding of any scroll view on a page that has chrome floating over it. The bar and the FAB reserve no layout space, so a list that stops at its own last pixel hands the user a final row they can see and cannot tap. Both derive their numbers from `TimeBuddyBottomBar.reservedHeight` and `kFloatingActionButtonMargin`, so a per-page `120` invented at a call site drifts the moment the bar is retuned. |
| `ResponsiveLayout.isMobile(context)` / `.maxContentWidth` | `lib/app/widgets/responsive_layout.dart` | Every breakpoint question. The same `600` decides which nav chrome renders, where the date pill goes and how wide content may grow; hardcoding it in one of the three is how they drift apart. |
| `LiftedFab` | `lib/app/widgets/lifted_fab.dart` | Wrapping anything handed to `Scaffold.floatingActionButton`. It lifts only when the bottom bar is actually on screen (mobile, sub-page depth 0), which the page itself cannot know, since the sub-page that hides the bar is pushed *above* it. |
| `SubPageScope` / `subPageDepth` | `lib/app/widgets/sub_page_scope.dart` | Marking a pushed sub-page, and asking whether one is open. The chrome that reacts (bar, date pill, FAB lift) is built above the pushed route, so an `InheritedWidget` would flow the wrong way. Only `SubPageScope` writes the counter. |
| `ShellDatePill` | `lib/app/routes/app_shell.dart` | Placing a page's reference-day stepper. Below `600px` it renders in place, above it the sidebar owns the control, and a page that implements half of that rule shows two steppers on a tablet. |

### UI & Formatting

* Every user-facing string via slang (`t.section.key`), never hardcode
* Times rendered with `formatClock()` and offsets with `offsetLabel()`, never
  with an inline `DateFormat` or string interpolation
* Zone display names come from the location catalog, never from the raw IANA id.
  `America/Sao_Paulo` is an identifier; "Sao Paulo" is a label

## State Management

* **Bloc** for complex event-driven logic (Auth)
* **Cubit** for everything else (Board, Grid, WorldClock, Planner, Converter,
  Preferences, Startup). Theme mode, both palettes and the locale tag are fields
  of Preferences, not cubits of their own

### Rules

* UI must not contain business logic
* Cubits/Blocs orchestrate, UseCases execute logic
* State must be immutable

### Lifecycle

* Session-independent services and cubits are singletons
  (`registerLazySingleton` in `lib/app/di/injection_container.dart`): `Clock`,
  `LocalStore`, `TimeZoneEngine`, `TickerService`, `Uuid`,
  `PreferencesLocalDataSource`, `PreferencesRepository`, `PreferencesCubit`,
  `BoardLocalDataSource`, `BoardRepository`, `CityCatalogRepository` and
  `BuildGridUseCase`. `AuthBloc` and `StartupCubit` join them in M3.
  `CityCatalogRepository` is a singleton because the parsed catalog *is* the
  cache: a factory would re-read a 500-row asset on every keystroke in the city
  picker. `BuildGridUseCase` is pure and stateless, so one instance costs
  nothing and saves the grid cubit from building one per rebuild. `Uuid` is
  registered rather than called statically so a test can hand `BoardCubit` a
  counter and assert on the ids it wrote.
* `PreferencesCubit` is the **single source of truth for theme mode, both
  palettes and the locale tag**. There is deliberately no `ThemeCubit`,
  `LightPaletteCubit`, `DarkPaletteCubit` or `AppLocaleCubit`: those are fields
  of one synced document, and two cubits persisting the same field are two
  sources of truth for it, which is one bad merge away from silently resetting a
  palette the user chose. `app_widget` reads the preferences state, reassigns
  `AppColors.light` / `AppColors.dark`, and only then builds `MaterialApp`.
* `BoardCubit` is session-scoped: `AppShell` creates it through `BlocProvider`
  and starts its load, so it lives exactly as long as the shell and is
  deliberately **not** in `GetIt`, where a stray `sl<BoardCubit>()` could hand
  out a second board. The shell rather than a page, because it is the only
  widget that is an ancestor of every page reading the board *and* is built once
  per session: loading in the grid page would re-run on every visit and leave
  the locations page loading the same document a second time, which is two
  answers to "is the board ready". It takes no `userId` yet; M3 resolves one
  from `AuthBloc.state` at mount time, and `StartupCubit` takes the load over.
* Page-scoped cubits are created per visit by their page and disposed with it:
  `TimeGridCubit` by `TimeGridPage`, `LocationSearchCubit` by the add-location
  sheet. `WorldClockCubit`, `MeetingPlannerCubit` and `TimeConverterCubit` join
  them in M4. They read `BoardCubit` and `PreferencesCubit` and own only view
  state (reference date, cursor, query); every board mutation goes back through
  `BoardCubit`, so there is one owner of the list of places.

## Performance

* **One ticker for the whole app.** `TickerService`
  (`lib/core/time/ticker_service.dart`) exposes a single broadcast
  `Stream<DateTime>` at 1 Hz. A `Timer.periodic` per clock tile means N timers
  and N full rebuilds per second on a page that may list 30 cities.
* The ticker drops to 1/60 Hz when no visible widget needs seconds, and pauses
  entirely when the app is backgrounded (`AppLifecycleState.paused`).
* Rebuild only the leaf that shows the time. A clock row is a `StreamBuilder`
  around the digits, not around the row.
* Avoid unnecessary rebuilds (use `const`, selectors, split widgets)
* Lists must use lazy builders (`ListView.builder`, etc.)
* The grid is a two-axis scroll view with a pinned first column; it must not
  build every column of every row eagerly
* Avoid heavy work on the UI thread. The city catalog (500 entries) is parsed
  once and kept in memory, pre-folded into its search keys so a keystroke walks
  strings that are already index keys. `main` warms it without awaiting it, so
  the parse never delays the first frame

## Firestore Rules

```
users/{userId}
users/{userId}/settings/board
users/{userId}/settings/preferences
```

### Guidelines

* A user can read and write only their own `users/{userId}` subtree. There is no
  cross-user read path and no public collection.
* Reads are by document id only. No queries, no indexes, no unbounded scans.
* The whole remote state is 2 documents per user, so a full sync is 2 reads.

## Firebase: Firestore Collections

```
users/{userId}                       → name, email, photoUrl, createdAt
users/{userId}/settings/board        → homeZoneId, locations[], revision, updatedAt
users/{userId}/settings/preferences  → themeMode, lightPalette, darkPalette, hourFormat, weekStartsOn, workingHours { start, end }, locale, revision, updatedAt
```

`locations[]` entry shape:

```
{ id, zoneId, label, countryCode, sortIndex, addedAt }
```

> `zoneId` is the IANA identifier and the only field the engine reads.
> `label` and `countryCode` are display data denormalized from the city catalog
> at save time, so a board still renders if a future catalog drops that city.
